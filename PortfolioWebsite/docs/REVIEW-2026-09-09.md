# Homepage and editing consistency: pre-change findings

Compared the implementation with docs/PORTFOLIO-SPEC.md and the September 9 change request before revision.

- Biography: save a multi-paragraph biography and edit its second paragraph. About renders the change; HomeView splits on blank lines and discards it. Both views must use the same saved biography. Public production pages remain build snapshots by design.
- Dates: open project Details, Education, and Experience. All accept arbitrary text, use inconsistent labels, and have no calendar. New projects default to just the year. Public views echo raw text without formatting or validation.
- Tools: profile Tools offers searchable software and custom entries; project Review requires comma-separated free text. Reuse the software picker in both workflows.
- Featured projects: the first array entry is always large, with no owner control and no description. Add an explicit, single featured selection, including replacement and removal.
- Homepage: the tagline is hardcoded and there is no banner field. Add editable content using the existing image upload/crop system, including removal.

Owner content and credentials are read-only during this work. Changes and browser mutations use isolated QA fixtures. Existing partial dates must retain their original precision; never invent a month/day for owner records.

Initial scores were not numerically assessed. Exactly one final independent critic pass will follow implementation checks and screenshot inspection, with scores and unresolved findings recorded in CRITIC-REPORT.md.
